<objective>
Enforce blur budgets (PERF-01) and suppress unnecessary GPU compositing layers on mobile (PERF-02) so glass effects stay smooth on mid-range Android devices at viewports below 768px.

Purpose: Mid-range Android CPUs (e.g., Snapdragon 6xx) struggle with backdrop-filter blur values above 20px. The current design system uses 24–60px blurs as desktop defaults. Without a mobile budget, scrolling through glass surfaces causes frame drops. Suppressing will-change on static glass elements prevents Chrome from promoting them to compositor layers unnecessarily.

Output: A single @media (max-width: 767px) block in theme.css that caps all blur tokens to 14–20px range, and a matching block in liquid-glass.css that removes will-change from non-animated glass surfaces on mobile.
</objective>

```css
/* ================================================
   Phase 75 (PERF-01): Mobile blur budget
   Cap all backdrop-filter blur values to 14-20px on
   viewports below 768px. Mid-range Android CPUs cannot
   sustain 60fps with blur > 20px during scroll.

   Tokens in scope:
   - --liquid-blur-md: 24px desktop → 16px mobile
   - --liquid-blur-lg: 40px desktop → 18px mobile
   - --liquid-blur-xl: 60px desktop → 20px mobile
   - --liquid-clear-blur: 20px desktop → 16px mobile (dark: 24→16)
   Tokens already safe (≤ 20px), no change needed:
   - --liquid-blur-sm (16/18px)
   - --liquid-nav-blur (16/18px)
   ================================================ */
@media (max-width: 767px) {
  :root {
    --liquid-blur-md: 16px;
    --liquid-blur-lg: 18px;
    --liquid-blur-xl: 20px;
    --liquid-clear-blur: 16px;
  }

  .dark {
    --liquid-blur-md: 16px;
    --liquid-blur-lg: 18px;
    --liquid-blur-xl: 20px;
    --liquid-clear-blur: 16px;
  }
}
```

Note: --liquid-blur-sm and --liquid-nav-blur are already 16px/18px on desktop — they are already within budget and do NOT need mobile overrides.

Note: The -webkit-backdrop-filter Safari fallback lines in liquid-glass.css use hardcoded pixel values (e.g., `blur(24px)`). These hardcoded values bypass the token system entirely and are NOT updated by this media query. That is acceptable — Safari on iOS uses Metal for blur and handles larger values efficiently. The token-based `backdrop-filter:` lines (which target Chrome/Firefox Android) ARE governed by this media query.

  <action>

This block suppresses will-change on mobile to prevent Chrome from creating unnecessary GPU compositing layers for static glass surfaces:

```css
/* ================================================
   Phase 75 (PERF-02): Mobile compositing layer budget
   Suppress will-change on static glass elements at mobile
   breakpoint (< 768px). On mid-range Android, each
   will-change: backdrop-filter or will-change: transform
   forces a GPU compositing layer. More than 4 simultaneous
   compositing layers degrade scroll performance.

   Rationale for each suppression:
   - .liquid-card::before — glint animation uses
     will-change: background-position unconditionally.
     On mobile the 6s glint cycle is barely noticeable
     but the promoted layer wastes GPU memory.
   - Button/shimmer will-change is already lazy (applied
     on :hover only) — hover doesn't fire on touch so
     those do NOT need suppression here.
   ================================================ */
@media (max-width: 767px) {
  /* Suppress glint animation compositing layer on mobile */
  .liquid-card::before {
    will-change: auto;
  }

  /* Reduce animation duration on glint to cut GPU work on mobile */
  @keyframes glint {
    0% { background-position: 200% 0; }
    100% { background-position: -200% 0; }
  }

  .liquid-card::before {
    animation-duration: 12s; /* halve repaint frequency on mobile */
  }
}
```

Note on PERF-02 layer count: The production HTML pages (index.html, checkup.html, consultations.html, treatment-abroad.html) do NOT use any liquid-* glass classes — they load only css/styles.css which has zero backdrop-filter. PERF-02 therefore applies exclusively to the Next.js design-system scaffold (src/styles/). In that scaffold, sections use at most: 1 header (liquid-nav) + cards in view (liquid-card). Ensuring .liquid-card::before does not add a promoted layer on mobile keeps the worst-case count at header (1) + visible cards (2-3) = 3-4 layers, within budget.
  </action>
