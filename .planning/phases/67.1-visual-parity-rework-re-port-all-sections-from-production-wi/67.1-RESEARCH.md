# Phase 67.1: Visual Parity Rework - Research

**Researched:** 2026-04-11
**Domain:** HTML/CSS/JS visual parity between production vanilla site and Next.js migration
**Confidence:** HIGH

## Summary

The v6.0 Next.js migration (Phases 59-67) ported the index page and contacts page to React components using Tailwind CSS v4 with Liquid Glass design system classes. However, the Next.js components diverge significantly from the production vanilla HTML/CSS site in typography scale, spacing rhythm, section backgrounds, component structure, button styling, and layout patterns. The production site uses a carefully tuned BEM-based CSS system with design tokens (`--font-size-base: 18px`, `--section-padding-mobile: 48px`, `--section-padding-desktop: 100px`) that the Next.js version does not match -- it uses generic Tailwind spacing that produces visually different results.

Additionally, three full service pages exist in production (consultations.html, treatment-abroad.html, checkup.html) that have NO Next.js equivalents at all. The contacts page in Next.js was reimagined (with coordinator cards, glass contact methods, trust badges) rather than ported from the production contacts page, which does not exist as a separate HTML file -- contacts are part of the lead form section on every page.

**Primary recommendation:** Systematically diff each production section against its Next.js counterpart, correcting every visual property to match production CSS values exactly. Then create the three missing service pages by porting their HTML structure to React components. Use the production CSS custom properties as the single source of truth for all visual values.

1. **Production CSS** (`css/styles.css`) -- every visual value comes from here

### Recommended Approach

```
For each section:
1. Read the production HTML structure
2. Read the production CSS for that section

5. Where production uses plain .card / .button classes, use plain Tailwind equivalents

```

### Key Decision: Glass vs Plain

The production index.html does NOT use any Liquid Glass classes. The production pages use plain BEM CSS classes (`.card`, `.button--primary`, `.hub-service`, etc.). The Liquid Glass system was built in v4.0-v5.0 for the vanilla HTML site, and those pages do reference glass classes -- but the **index.html that was ported** does not.

However, per the project memory rule: "NEVER replace glass classes with plain bg-white/shadow when porting to React." This creates a tension:
- Production index uses NO glass
- Next.js index uses glass everywhere
- Memory rule says don't remove glass

**Resolution:** The task says "1:1 visual parity with production." If production has no glass on index page sections, the Next.js version should match production. BUT -- if the production site was UPDATED to have glass after the v4.0/v5.0 phases, then glass is correct. The audit screenshots (from `audit-chromium-index.png`) show a different design altogether with photos and a more modern layout -- suggesting the "production" reference may be the v5.0 Liquid Glass vanilla HTML site, not the pre-glass v1.0 site.

**Recommendation for planner:** The planner should clarify with the user which version of "production" is the visual target. The HTML files in the repo root (index.html, etc.) represent the shipped production site. The glass system exists in the vanilla CSS (liquid-glass.css in `src/styles/`) but is NOT applied to index.html. The audit screenshots show a design that has glass applied. This ambiguity must be resolved.

## Common Pitfalls

### Pitfall 1: Tailwind Default Scale vs Production Design Tokens
**What goes wrong:** Using Tailwind's default spacing/typography scale produces values that are close but not identical to production custom properties. `py-12` is 48px which matches `--section-padding-mobile: 48px`, but `text-3xl` is 30px which does NOT match `--font-size-h1: clamp(2.5rem, 5vw, 3.5rem)`.
**Why it happens:** Tailwind's scale was designed for general use; the production site has custom clamp() values tuned for the 45+ audience.
**How to avoid:** Use arbitrary values in Tailwind (`text-[clamp(2.5rem,5vw,3.5rem)]`) or define custom Tailwind theme values matching production tokens.
**Warning signs:** Text looks "small" or "thin" compared to production.

### Pitfall 2: Glass Where Production Has None
**What goes wrong:** Applying `liquid-card`, `liquid-regular`, `liquid-btn-primary` to sections that use plain `.card` and `.button--primary` in production makes the site look like a different design.
**Why it happens:** Phases 59-67 assumed the migration target was the glass-enhanced design from v4.0/v5.0 development.
**How to avoid:** Compare directly against production HTML files, not the glass design system docs.
**Warning signs:** Sections have frosted glass backgrounds, blur effects, and refraction where production has flat white cards.

### Pitfall 3: Missing Service Pages
**What goes wrong:** Index page links to `/consultations`, `/treatment-abroad`, `/checkup` which return 404 in Next.js.
**Why it happens:** v6.0 migration only ported index and contacts pages.
**How to avoid:** Create all three service pages before considering phase complete.
**Warning signs:** Clicking any service card CTA button leads to a blank/error page.

### Pitfall 4: Footer Background Color
**What goes wrong:** Footer uses `bg-mu-text-900` (#1B212C) in Next.js but production uses `--color-navy` (#1A365D). The navy blue is distinctly different from near-black.
**Why it happens:** The color token was mapped incorrectly during migration.
**How to avoid:** Use the exact production hex value.
**Warning signs:** Footer looks dark/black instead of dark navy blue.

### Pitfall 5: Base Font Size Cascade
**What goes wrong:** Setting `font-size: 1.125rem` on `html` affects ALL Tailwind rem-based values. `text-lg` (1.125rem) becomes 1.125 * 1.125 = 1.265rem instead of 18px.
**Why it happens:** Tailwind uses rem units relative to the root font size.
**How to avoid:** Either (a) keep root at 16px and adjust individual text sizes, or (b) set root to 18px and recalculate all Tailwind values. Option (a) is safer.
**Warning signs:** All spacing and text sizes are slightly inflated.
