<!-- Tailwind binary state -->

The `tailwindcss` standalone CLI binary is gitignored at `.gitignore` line 13: `tailwindcss` (with the comment "Tailwind CSS standalone CLI binary (~73MB, download with curl)"). On a fresh clone the binary is absent. The currently-checked-in working tree has a `tailwindcss` binary (verified during planning: macOS arm64, Mach-O 64-bit, version 4.2.2).

For `make build` to work on a fresh clone, the Makefile must include an `install-tailwind` target that downloads the binary from GitHub releases when it's missing, and `make build` must depend on it. The download URL pattern for v4.2.2:

  https://github.com/tailwindlabs/tailwindcss/releases/download/v4.2.2/tailwindcss-{platform}-{arch}

Where `{platform}` is `macos`, `linux`, or `windows` and `{arch}` is `arm64` or `x64`. The Makefile detects the platform/arch via `uname -s` and `uname -m` and constructs the URL.

Pin the version to match the current local binary (v4.2.2) to avoid surprises — running `./tailwindcss --help | head -1` during planning showed `≈ tailwindcss v4.2.2`.

<!-- build-pages.sh interface (from Plan 02) -->

`scripts/build-pages.sh` is a POSIX-sh script. It accepts an optional list of HTML files as positional args, defaults to the 6 production pages when called with no args. It exits 0 on success and non-zero on any error (missing partials, malformed BUILD:vars block, missing markers, etc.). Make `make build` invoke it with no args (relies on the default file list).

<!-- Pre-commit hook contract -->

The hook lives at `scripts/hooks/pre-commit` (repo-tracked, executable). It is NOT placed at `.git/hooks/pre-commit` directly, because that path is not tracked in git. Instead, `make install-hooks` creates a symlink:
  ln -sf ../../scripts/hooks/pre-commit .git/hooks/pre-commit

(The relative target `../../scripts/hooks/pre-commit` works because `.git/hooks/pre-commit` resolves it relative to its own directory: `.git/hooks/../../scripts/hooks/pre-commit` = `./scripts/hooks/pre-commit`. This is the standard pattern used by repos with tracked git hooks.)

The hook behavior:
  1. Run `make build` (which compiles Tailwind and runs the partial splicer)
  2. After build, check `git diff --quiet -- '*.html'`
  3. If the diff is empty: exit 0 (hook passes, commit proceeds)
  4. If the diff is non-empty (build regenerated HTML — chrome partials changed but contributor didn't run `make build` before staging):
     - Print a clear multi-line error message to stderr explaining what happened and how to fix it
     - List the changed HTML files via `git diff --name-only -- '*.html'`
     - Exit 1 (commit blocked)

The hook does NOT auto-`git add` the regenerated files (locked decision from v3.2 kickoff: "auto-add hides drift from the contributor").

Performance note: `make build` includes the Tailwind compile step which takes ~1-2s on this codebase, plus the splicer (~50ms for 6 pages). Total hook overhead: ~2s per commit. Acceptable for the safety guarantee.

    ```sh
    #!/bin/sh
    # scripts/hooks/pre-commit
    # Phase 39 / LAYOUT-13
    # First git hook in this repo.
    # Runs `make build` to compile Tailwind CSS and splice chrome partials,
    # then enforces the byte-identity gate: if the build modified any HTML page,
    # the commit is blocked until the contributor stages the regenerated pages.
    #
    # Install with:  make install-hooks
    # The install-hooks target creates a symlink at .git/hooks/pre-commit
    # that points to this file (scripts/hooks/pre-commit), so this file is the
    # single source of truth for hook content and lives under version control.
    #
    # Behavior:
    #   1. Run `make build`
    #   2. If build fails -> hook exits non-zero, commit blocked
    #   3. If build succeeds, check `git diff --quiet -- '*.html'`
    #   4. If diff is non-empty (chrome partials changed and HTML pages were regenerated):
    #      - Print clear instructions to stderr
    #      - List the modified pages
    #      - Exit 1 (commit blocked) — contributor must `git add` the pages and re-commit
    #   5. If diff is empty: exit 0 (commit proceeds)
    #
    # The hook does NOT auto `git add` the regenerated files. That would hide chrome
    # drift from the contributor; explicit re-staging is the intended UX.

    set -eu

    # Find repo root (so the hook works regardless of CWD when invoked by git)
    REPO_ROOT=$(git rev-parse --show-toplevel)
    cd "$REPO_ROOT"

    echo "[pre-commit] running 'make build'..."
    if ! make build; then
      echo "[pre-commit] FAIL: make build returned non-zero" >&2
      echo "[pre-commit] fix the build error and re-commit" >&2
      exit 1
    fi

    if ! git diff --quiet -- '*.html'; then
      DRIFTED=$(git diff --name-only -- '*.html')
      cat >&2 <<EOF
    [pre-commit] BLOCKED: chrome partials changed but the regenerated HTML pages were not staged.

    The following pages were updated by 'make build':
    $DRIFTED

    To unblock this commit:
      1. git add $(echo "$DRIFTED" | tr '\n' ' ')
      2. Re-run your commit command

    Why this matters: the chrome partials in partials/*.html are the single source of
    truth for the header / footer / sticky-bar / mobile-menu. When you change a partial,
    'make build' propagates the change into all 6 production HTML pages. Both the
    partial change and the regenerated pages must land in the same commit.
    EOF
      exit 1
    fi

    echo "[pre-commit] OK: byte-identity gate passed"
    exit 0
    ```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub releases CDN→local filesystem | `make install-tailwind` downloads a binary from a public URL — supply-chain trust boundary |
| .git/hooks/pre-commit symlink→scripts/hooks/pre-commit | git executes the symlink target as the contributor's user; the target must be repo-tracked, never network-fetched |
| pre-commit hook→make build | Hook delegates to `make build` which exec's tailwindcss + scripts/build-pages.sh — no untrusted input enters the hook |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-39-03-01 | Tampering | tailwindcss binary download from GitHub releases (`make install-tailwind`) | mitigate | URL is HTTPS-only (`https://github.com/tailwindlabs/tailwindcss/releases/...`), version is pinned to `v4.2.2` so the same release is fetched on every clean clone (no "latest" floating tag), and `curl -fL` fails on non-2xx responses. The binary lives outside git tracking (.gitignore) so a compromised download cannot silently replace a tracked artifact. As a defense-in-depth, future enhancement could verify a SHA256 checksum (Tailwind publishes them with each release) — this is documented in docs/BUILD.md as a follow-up but not required for v3.2 (the release URL itself is the trust anchor). |
| T-39-03-02 | Elevation of Privilege | scripts/hooks/pre-commit running as the contributor's user with full repo access | mitigate | The hook is repo-tracked in `scripts/hooks/pre-commit` and reviewed via PR like any other code. The `make install-hooks` target creates a symlink to the tracked file rather than copying — so updates to the tracked hook propagate immediately on the next commit (no stale-copy vector). The hook is NEVER fetched from a network URL. The hook script is POSIX sh + git invocations + make invocations only — no eval, no network calls. |
| T-39-03-03 | Tampering | Pre-commit hook bypass via `git commit --no-verify` | accept | A malicious or rushed contributor can always bypass with `--no-verify`. The byte-identity gate is also enforceable via `make check` in CI when CI is added in v3.3+ (per REQUIREMENTS.md "Out of Scope" — CI is deferred). For solo-developer scope (v3.2), pre-commit + manual `make check` is sufficient. |
| T-39-03-04 | Information Disclosure | docs/BUILD.md exposing build internals | accept | Build pipeline documentation contains no secrets — only commands, file paths, and the variation table that's also visible in the public-facing HTML. |
| T-39-03-05 | Denial of Service | `make build` running on every commit adds ~2s of latency to the contributor's commit flow | accept | 2s is well below the threshold for contributor friction. The hook can be temporarily bypassed with `--no-verify` for known-safe doc-only commits if the latency becomes objectionable. The safety guarantee (chrome drift impossible at commit time) is worth the latency. |
| T-39-03-06 | Tampering | docs/BUILD.md "manual install" instructions could drift from actual Make targets | mitigate | docs/BUILD.md references the exact Make targets by name (`make install-hooks`, `make build`, `make install-tailwind`) and they are part of the verification block — if a target is renamed in the Makefile, the doc grep verification fails and the contributor must update the doc in the same PR. |
